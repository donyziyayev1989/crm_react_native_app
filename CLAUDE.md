# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A small CRM for selling products in batches ("lots"), built with Expo (SDK 54, React Native 0.81, new architecture, React Compiler on) and Supabase (shared with the kurka.uz website project). The UI text and many code comments are in **Uzbek** (e.g. "Partiyalar" = lots, "Mijozlar" = customers, "Xaridlar" = orders). Keep that language for any new user-facing text.

## Commands

```bash
npm start                 # expo start (dev server; needs a dev client, not Expo Go — native Mapbox)
npm run android           # expo run:android (native build; /android is gitignored and regenerated by prebuild)
npm run web               # web build
npm run lint              # expo lint (eslint-config-expo)
npm test                  # jest (pure utils only: src/utils/__tests__)
npx jest src/utils/__tests__/phone.test.ts   # one test file
npx tsc --noEmit          # type-check (no script for it)
eas build -p android --profile production   # APK; production env vars live in eas.json
```

Backend (`supabase/`): migrations `0006..0016` (the `crm` schema, then the unified-database ones `0010..0016`) are authored in the kurka.uz repo's `supabase/migrations/` (one migration history for the shared project) and kept here as byte-identical copies; the `0099` cleanup stays only in kurka.uz and is applied after sign-off (see `supabase/README.md`). Edge Functions in `supabase/functions/` (`telegram-webhook`, `send-telegram`; see its README). Local test stack, integration test and cutover steps: `supabase/README.md`. Legacy Firebase code (`functions/`, `firestore.rules`, `firebase.json`) stays only until cutover; Firestore → Supabase data copy: `scripts/migrate-firestore-to-supabase/`.

Tests: pure helpers in `src/utils` and `src/services/query.ts`; `src/services/__tests__/database.integration.test.ts` runs the data layer against a local Supabase stack and is skipped without `SUPABASE_TEST_*` env (jest-expo preset, `moduleNameMapper` for the `@/` aliases in `package.json`). Screens are verified manually on a dev client.

## Architecture

### Routing (expo-router, `src/app/`)
- `_layout.tsx` is the root Stack. It also mounts `GlobalChat`, a Telegram chat overlay that any screen opens through the `chatEvents` pub/sub in `src/utils/chat_events.ts` (used by `utils/actions.tsx` `openTelegram` and the messages screen).
- `(tabs)/_layout.tsx` declares every tab. Several are hidden with `href: null` (orders, products, tags, profile, leads) and reached by navigation. The center `addOrder` tab is a fake button: it opens `OrderModal` and never navigates to the `addOrder` route.
- Feature folders (`customers/`, `lots/`, `orders/`, `leads/`) have their own `_layout.tsx` Stack with `[id].tsx` detail and `edit/[id].tsx` screens.
- Typed routes are enabled (`experiments.typedRoutes`).

### Supabase data layer (the most important thing to understand)
One `supabase-js` client (`src/supabase/client.ts`) serves native and web; CRM tables live in the `crm` Postgres schema (default for the client). Tables shared with the website live in `public` (`lots`, `tags`, `lost_products`, `lot_expenses`, `products`, `faqs`, plus `profiles`) and are registered with `schema: "public"`; `products` and `faqs` are localized on the site (`name->>uz` jsonb), so they go through `productAdapter`/`faqAdapter` in `src/services/adapters.ts` (`fromRow`/`toRow`, `Product.price` is `number | null`). `confirmLead(...)` in `database.tsx` wraps the `crm.confirm_lead` RPC.
- `src/supabase/auth.ts`: Google `idToken` → `signInWithIdToken`; `onAuthStateChanged`, `signOut`, and `auth.currentUser?.uid` (sync). Only active staff in `public.profiles` (admin/operator) may sign in (`NoAccessError` otherwise). Staff are created by an admin / the migration script, not by the app.
- `src/services/database.tsx` is the **only** data access layer and keeps the old Firestore-style API: `db.<collection>` gives `list/get/create/update/delete/set/watch/watchDoc/sum`, and `where/orderBy/limit` are our own builders (`services/query.ts`) that translate to PostgREST. Import from here, not `supabase` directly. Field names are the old Firestore ones; `lotId→lot_id`, `createdAt→created_at`, `photoURL→photo_url` etc. are mapped in `query.ts`; `user_id: ""` is stored as null.
- `watch()` = first fetch + Realtime `postgres_changes` (tables have `replica identity full`). Unfiltered `orderBy`-only watches are patched in memory and cached in AsyncStorage (`services/cache.ts`, cleared on sign out); filtered ones refetch on a relevant event. `list()` pages through PostgREST's 1000-row cap. There is no offline write queue (unlike Firestore).
- `src/providers/ReferenceData.tsx` holds **one** `watch` per reference collection (regions, districts, products, tags, lots, users, customers) for the whole app. Screens read them with `useRefData()` and `useDistrictsOfRegion()`; do not open your own `watch`/`list` on these collections. Per-lot order totals use `db.orders.sum("product_count", where("lotId","==",id))` (server RPC).
- Never rely on Firestore-only features: prefix search (`>= q` + `<= q + ""`) is converted to case-insensitive `ilike 'q%'`; keep other queries to `==, !=, <, <=, >, >=, in, array-contains`.
- To add a collection: interface in `src/interfaces/index.ts`, a table + RLS policy + realtime publication in a `crm` migration (or `public` if the website shares it, with `schema: "public"`), and register it in the `db` object (`createCollection`, or `createSubCollection` for scoped child tables like `lead_messages` with `chat_id`).

### Data model
Flat `crm.*` tables (see `supabase/migrations/0006_crm_schema.sql`): `orders`, `customers`, `regions`, `districts`, `rates`, `leads`, `lead_chats`, `lead_messages`, `settings`, `bot_sessions` (service role only) and the read-only view `users` (profiles + auth.users). `lots`, `tags`, `lost_products`, `lot_expenses`, `products`, `faqs` now live in `public` (`0011..0013`; `crm.orders.product_id` points to `public.products`); the same-named `crm.*` views are temporary compat views for old APK builds (no Realtime) and `*_legacy` tables are dropped by `0099`. `crm.leads` is unified: `source` (`website`/`telegram`/`manual`), `items` jsonb, `number`, `total`, `has_unpriced`, `address`, `locale`, `customer_id`, `order_ids`, `legacy`. Website orders are created as leads by `public.create_lead` (old `public.orders` were backfilled into leads by `0015`); an operator confirms a lead into CRM orders with `crm.confirm_lead` (`0016`). Relations are plain ID fields (`lotId`, `customer_id`, `tag_ids`, …). Region and district are stored **denormalized by name** (`region_name`, `district_name`) on orders and customers. `src/firebase/scripts/{regions,districts}.js` hold the region/district seed data.

Security: RLS on every `crm` table allows only active staff (`crm.is_staff()` → `public.app_role()` in admin/operator). Both roles have full access to `crm.*`; on the shared `public` tables the operator is read-only and only admin writes (the app hides those controls for operators).

### Telegram bot → leads (`supabase/functions/`)
`telegram-webhook` (Deno Edge Function, service role, `verify_jwt=false`, checks `X-Telegram-Bot-Api-Secret-Token`) runs the customer-facing bot. Logic lives in `_shared/bot.ts` (pure, tested with `node --test "supabase/functions/_tests/*.test.mjs"`). It keeps conversation state in `crm.bot_sessions`, serves FAQs from `public.faqs` (cached) and `crm.settings.about_us`, lists active `public.products` (both read through the injected `pub` client, `crm` is the other), reverse-geocodes locations with OSM Nominatim, writes `crm.leads` with `source: "telegram"` and `items`, and mirrors chat messages via the `crm.bot_append_customer_message` RPC. Operator replies from the app go through the `send-telegram` function (JWT + active staff); the bot token is never in the app.

### Maps
`@rnmapbox/maps` (native only). `app.config.js` injects `RNMAPBOX_MAPS_DOWNLOAD_TOKEN` from the environment into the plugin config at build time. `services/mapboxService.ts` (directions/matrix API calls) and `services/routeService.ts` drive `LotMapView`, which plans delivery routes for a lot's orders (`app/lots/[lotId]/map.tsx`).

### Styling
NativeWind v4 (Tailwind 3) with `className`. The entry stylesheet is `src/app/globals.css`, wired in `metro.config.js` and `babel.config.js`. Some layouts (e.g. the tab bar) still use `StyleSheet`.

## Conventions and gotchas
- Path aliases (tsconfig): `@/*` → `src/*`, plus `@components/*`, `@interfaces/*`, `@utils/*`, `@assets/*`, `@app/*`. Pure utils in `src/utils` import siblings with relative paths so Jest resolves them.
- Shared helpers — use these instead of re-implementing: phone (`utils/phone.ts`: `digitsOnly`, `toLocal9`, `phonesMatch`, `phoneVariants` for `where("phone","in",…)`, `formatPhone`), money/date (`utils/format.tsx`: `formatMoney` is bare digits, `formatSum` includes `" so'm"`, `formatTime`, `formatDateLabel`, `parseNum`), region/district matching (`utils/regions.ts`: names in the DB vary in apostrophes/spelling and `districts.regionId` uses legacy aliases — always go through `findRegion`/`districtsOfRegion`), lot lost totals (`utils/lots.ts: lostPercent`, `services/lotStats.ts: recalcLostTotal`). `WithId<T>` in `interfaces` replaces `T & { id: string }`.
- Shared UI: region/district pickers are always `RegionDistrictSelect` (form stores **names**, not ids); list+modal CRUD screens use `SimpleCrudScreen` (see `products/index.tsx`); swipeable rows use `useSwipeableRows`; centered spinners use `Loading`.
- `OrderModal` is mounted from six screens. Its init effect runs once per open (`initializedRef`); do not add provider arrays to effects that reset form state.
- Environment: client config comes from `EXPO_PUBLIC_*` vars in `.env` (`EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY`, `EXPO_PUBLIC_MAPBOX_ACCESS_TOKEN`, `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`). `.env` is gitignored.
- Production builds strip `console.*` (`babel-plugin-transform-remove-console`).
- The filesystem is case-insensitive (Windows) and component filenames are PascalCase (`CustomerForm.tsx`, `Search.tsx`), but git has tracked some under lowercase names. Match the casing on disk in imports, and use `git mv` when renaming only the case.
