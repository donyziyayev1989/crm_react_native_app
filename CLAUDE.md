# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A small CRM for selling products in batches ("lots"), built with Expo (SDK 54, React Native 0.81, new architecture, React Compiler on) and Firebase. The UI text and many code comments are in **Uzbek** (e.g. "Partiyalar" = lots, "Mijozlar" = customers, "Xaridlar" = orders). Keep that language for any new user-facing text.

## Commands

```bash
npm start                 # expo start (dev server; needs a dev client, not Expo Go — native Firebase/Mapbox)
npm run android           # expo run:android (native build; /android is gitignored and regenerated by prebuild)
npm run web               # web build (uses the Firebase JS SDK instead of native)
npm run lint              # expo lint (eslint-config-expo)
npm test                  # jest (pure utils only: src/utils/__tests__)
npx jest src/utils/__tests__/phone.test.ts   # one test file
npx tsc --noEmit          # type-check (no script for it)
eas build -p android --profile production   # APK; production env vars live in eas.json
```

Cloud Functions (`functions/`, Node 20, plain JS): `cd functions && npm install`, then `firebase deploy --only functions` (and `firebase deploy --only firestore:rules` for `firestore.rules`).

Tests cover only the pure helpers in `src/utils` (jest-expo preset, `moduleNameMapper` for the `@/` aliases in `package.json`). Screens are verified manually on a dev client.

## Architecture

### Routing (expo-router, `src/app/`)
- `_layout.tsx` is the root Stack. It also mounts `GlobalChat`, a Telegram chat overlay that any screen opens through the `chatEvents` pub/sub in `src/utils/chat_events.ts` (used by `utils/actions.tsx` `openTelegram` and the messages screen).
- `(tabs)/_layout.tsx` declares every tab. Several are hidden with `href: null` (orders, products, tags, profile, leads) and reached by navigation. The center `addOrder` tab is a fake button: it opens `OrderModal` and never navigates to the `addOrder` route.
- Feature folders (`customers/`, `lots/`, `orders/`, `leads/`) have their own `_layout.tsx` Stack with `[id].tsx` detail and `edit/[id].tsx` screens.
- Typed routes are enabled (`experiments.typedRoutes`).

### Dual Firebase SDK (the most important thing to understand)
The app uses the **Firebase JS SDK on web** and **@react-native-firebase on native**, chosen at runtime by `Platform.OS`:
- `src/firebase/firebase.tsx` exports `auth`, `database`, and `federated*` auth helpers (sign-in, sign-out, onAuthStateChanged, Google credential) that pick the right SDK.
- `src/services/database.tsx` is the **only** data access layer. `db.<collection>` gives `list/get/create/update/delete/set/watch/watchDoc/sum` for each collection, and the query helpers (`where`, `orderBy`, `limit`, …) are re-exported from the right SDK. Import from here, not from `firebase/firestore` directly, or the code breaks on one platform. Small SDK differences (e.g. how `exists` is exposed on a snapshot) are handled inside the wrapper (`snapExists`).
- `src/providers/ReferenceData.tsx` holds **one** `watch` per reference collection (regions, districts, products, tags, lots, users, customers) for the whole app. Screens read them with `useRefData()` (arrays plus `*ById` maps) and `useDistrictsOfRegion()`; do not open your own `watch`/`list` on these collections. Single documents use `db.<col>.watchDoc(id, cb)`; per-lot order totals use `db.orders.sum("product_count", where(...))` (one aggregate read per lot instead of watching all orders).
- `list()` always hits the server; `watch()` serves from the local cache. Prefer `watch` for anything shown on screen. Never combine `where` on one field with `orderBy` on another in one query (needs a composite index) — sort in JS instead.
- To add a collection: add its interface in `src/interfaces/index.ts` and register it in the `db` object (`createCollection` or `createSubCollection` for nested ones like `lead_chats/{id}/messages`).

### Data model
Firestore is flat (see the header comment in `src/interfaces/index.ts`): top-level `lots`, `orders`, `customers`, `products`, `regions`, `districts`, `tags`, `rates`, `lost_products`, `lot_expenses`, `leads`, `lead_chats`, `faqs`, `settings`, `users`. Relations are plain ID fields (`lotId`, `customer_id`, `tag_ids`, …). Region and district are stored **denormalized by name** (`region_name`, `district_name`) on orders and customers. `src/firebase/scripts/migrate.js` seeds `regions`/`districts`.

Security rules (`firestore.rules`) only require an authenticated user.

### Telegram bot → leads (`functions/index.js`)
One HTTPS function, `telegramWebhook`, runs the customer-facing Telegram bot. It keeps conversation state in `bot_sessions`, serves FAQs from `faqs` (cached) and `settings/about_us`, lists `products`, reverse-geocodes shared locations with OSM Nominatim, and writes `leads`. It also mirrors chat messages into `lead_chats/{chatId}/messages`, which the app's Leads/Messages screens and `TelegramChat` read. The bot token comes from `EXPO_CRM_APP_TELEGRAM_BOT_TOKEN` in `functions/.env`.

### Maps
`@rnmapbox/maps` (native only). `app.config.js` injects `RNMAPBOX_MAPS_DOWNLOAD_TOKEN` from the environment into the plugin config at build time. `services/mapboxService.ts` (directions/matrix API calls) and `services/routeService.ts` drive `LotMapView`, which plans delivery routes for a lot's orders (`app/lots/[lotId]/map.tsx`).

### Styling
NativeWind v4 (Tailwind 3) with `className`. The entry stylesheet is `src/app/globals.css`, wired in `metro.config.js` and `babel.config.js`. Some layouts (e.g. the tab bar) still use `StyleSheet`.

## Conventions and gotchas
- Path aliases (tsconfig): `@/*` → `src/*`, plus `@components/*`, `@interfaces/*`, `@utils/*`, `@assets/*`, `@app/*`. Pure utils in `src/utils` import siblings with relative paths so Jest resolves them.
- Shared helpers — use these instead of re-implementing: phone (`utils/phone.ts`: `digitsOnly`, `toLocal9`, `phonesMatch`, `phoneVariants` for `where("phone","in",…)`, `formatPhone`), money/date (`utils/format.tsx`: `formatMoney` is bare digits, `formatSum` includes `" so'm"`, `formatTime`, `formatDateLabel`, `parseNum`), region/district matching (`utils/regions.ts`: names in the DB vary in apostrophes/spelling and `districts.regionId` uses legacy aliases — always go through `findRegion`/`districtsOfRegion`), lot lost totals (`utils/lots.ts: lostPercent`, `services/lotStats.ts: recalcLostTotal`). `WithId<T>` in `interfaces` replaces `T & { id: string }`.
- Shared UI: region/district pickers are always `RegionDistrictSelect` (form stores **names**, not ids); list+modal CRUD screens use `SimpleCrudScreen` (see `products/index.tsx`); swipeable rows use `useSwipeableRows`; centered spinners use `Loading`.
- `OrderModal` is mounted from six screens. Its init effect runs once per open (`initializedRef`); do not add provider arrays to effects that reset form state.
- Environment: client config comes from `EXPO_PUBLIC_*` vars in `.env` (Firebase config, `EXPO_PUBLIC_MAPBOX_ACCESS_TOKEN`, `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`, `EXPO_PUBLIC_BOT_TOKEN`). `.env` is gitignored.
- Production builds strip `console.*` (`babel-plugin-transform-remove-console`).
- The filesystem is case-insensitive (Windows) and component filenames are PascalCase (`CustomerForm.tsx`, `Search.tsx`), but git has tracked some under lowercase names. Match the casing on disk in imports, and use `git mv` when renaming only the case.
